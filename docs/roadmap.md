## Identity migration checkpoint

### Agreement and cost boundary

The maintainer explicitly authorizes a backward-incompatible identity-model migration, reports that current users have already been informed, and will handle communications. Prefer a small validated, extensible model now over carrying legacy hierarchy assumptions into more publications. This supersedes the earlier requirement to obtain approval for the pilot transition; it does not authorize removing publication holds or guessing source metadata. Old clients may become unsupported at the tested cutover. Do not spend effort implementing perpetual v1 projections, automatic full-history migration, filesystem symlinks, or a universal arbitrary-hierarchy engine.

Rough engineering estimate: **40,000–80,000 additional tokens of implementation/review work**, with substantial uncertainty. A working allocation is 8–15k for identity schemas and fixtures, 10–20k for tooling/content relocation, 15–30k for mobile discovery/storage/setup, and 7–15k for integration and recovery checks. This is a planning allowance, not measured usage, a provider billing quote, or knowledge of the account's remaining quota; repeated context/tool input and debugging can increase actual usage. ISBN search UI, new chapter conversion, audio, multi-profile UI, and infrastructure are outside this estimate.

This session records the requested fallback rather than beginning an unverified partial migration. No identity schema, source relocation, v2 output, client migration, or endpoint retirement is implemented by this checkpoint. A subsequent implementation session can proceed under the existing authorization without repeating the architecture discussion. No token budget or account balance has been supplied or reserved.
